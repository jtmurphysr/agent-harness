# agent-harness

An autonomous development harness that turns a PRD into a working codebase — no human-authored code required.

You write the intent. Agents decompose, implement, test, gate, merge, and learn.

---

## How It Works

```
PRD ──► prd-to-issues ──► Sequential Issue Dispatch ──► Agent Implementation
                                                              │
                                                        CI Gate (4-stage)
                                                              │
                                                        Auto-Merge ──► Compound Learning
                                                                              │
                                                                    docs/learnings/ ──► feeds next PRD cycle
```

The harness operates as a closed-loop pipeline:

1. **PRD → Issues** — An agent reads your PRD and generates a sequenced set of GitHub issues, each with full interface contracts, domain warnings, named test cases, and coverage requirements.

2. **Sequential Dispatch** — Issues are dispatched one at a time. Each issue's PR must merge before the next begins. No parallel work, no dependency conflicts.

3. **Agent Implementation** — A Claude Code agent reads `AGENTS.md` (the operating constitution), implements the issue, runs all quality gates, and opens a PR.

4. **CI Gate** — Four-stage pipeline: structural boundary linting → ruff + mypy strict → pytest with 85% coverage floor → auto-merge (if all pass and no `human-review` label).

5. **Compound Learning** — On every merge, a learning agent analyzes the delta between what was specified and what was delivered, writes structured learnings, and optionally updates `AGENTS.md`.

6. **Garbage Collection** — Weekly entropy pass checks for doc staleness, dead code, coverage regressions, dependency hygiene, and boundary drift.

## Architecture

```
agent-harness/
├── AGENTS.md                          ← Operating constitution for all agents
├── scripts/
│   ├── validate_harness.py            ← Structural linter (boundaries + coverage omit drift)
│   └── backfill_learnings.py          ← Retroactive learning extraction from completed projects
├── docs/
│   ├── issues/                        ← Issue specs generated by prd-to-issues
│   ├── learnings/                     ← Compound learnings from merged PRs
│   └── examples/                      ← Reference implementations from validated projects
├── .github/
│   ├── workflows/
│   │   ├── ci.yml                     ← 4-stage CI pipeline with auto-merge
│   │   ├── agent-dispatch.yml         ← Dispatches agent on `agent-task` label
│   │   ├── prd-to-issues.yml          ← Decomposes PRD into sequenced issues
│   │   ├── compound-learning.yml      ← Extracts learnings on every merge
│   │   ├── gc-agent.yml               ← Weekly entropy pass
│   │   └── close-issue-on-merge.yml   ← Auto-closes linked issues
│   └── ISSUE_TEMPLATE/
│       └── agent-task.md              ← Binding contract between intent and execution
└── pyproject.toml.template            ← Validated Python project configuration
```

## Key Concepts

### AGENTS.md — The Operating Constitution

Every agent reads this before doing anything. It defines module boundaries (enforced by AST-level linting), critical domain warnings, harness lessons learned from previous failures, the definition of done, and code conventions. Constitutional amendments require the `human-review` label.

### Issue Specs as Binding Contracts

Each issue contains: files to create/modify, interface contracts with full type signatures, domain warnings as DO/DON'T pairs, named test functions (not "write comprehensive tests"), per-file coverage requirements, coverage omit deltas for `pyproject.toml`, and an explicit out-of-scope section. The tighter the spec, the fewer degrees of freedom for agent drift.

### Structural Linting

`validate_harness.py` enforces two invariants at the AST level:

- **Module boundaries** — each layer can only import from explicitly allowed modules. Resolvers never call clients. Pipeline never imports auth. Models import nothing.
- **Coverage omit hygiene** — implemented modules (containing real logic, not stubs) cannot remain in the coverage omit list. Catches the drift that happens when a module graduates from stub to implementation but the omit entry stays behind.

### Compound Learning Loop

The harness improves over time. Every merged PR is analyzed for: specification quality (did the agent follow the contract?), scope discipline (did it creep into adjacent modules?), iteration patterns (did CI pass on first push?), and missing context (what would have prevented iteration?). Learnings feed back into the next `prd-to-issues` generation cycle.

## Getting Started

### Prerequisites

Before starting, confirm you have:
- [ ] GitHub repository with Actions enabled
- [ ] `ANTHROPIC_API_KEY` — your Anthropic key
- [ ] `GH_PAT` — a fine-grained GitHub PAT with scopes: `contents:write`, `pull-requests:write`, `issues:write`
- [ ] `gh` CLI authenticated locally (`gh auth status`)

---

### Step 1 — Bootstrap the Repo Locally

```bash
mkdir <repo-name> && cd <repo-name>
git init
git remote add origin git@github.com:<your-org>/<repo-name>.git
```

---

### Step 2 — Install Claude Code (GitHub App)

1. Go to → **github.com/apps/claude**
2. Click **Install**
3. Select the new repo

> Claude Code must be installed per repo. Don't assume it carries over from another.

---

### Step 3 — Set Repo Secrets

```
GitHub → Repo → Settings → Secrets and variables → Actions → New repository secret
```

| Secret | Value |
|---|---|
| `ANTHROPIC_API_KEY` | Your Anthropic key |
| `GH_PAT` | Your fine-grained PAT |

> If Agent Dispatch fails with auth errors later, the PAT is the first thing to revalidate.
> Run `gh auth status` and verify the PAT prefix matches what's in the secret.

---

### Step 4 — Scaffold the Harness

```bash
# Copy from this repo into your new project repo
cp -r path/to/agent-harness/{AGENTS.md,.github,pyproject.toml.template,scripts} .
```

Adapt the following before committing:

| File | What to change |
|---|---|
| `AGENTS.md` | Fill in placeholders: project name, module boundaries, stack, domain warnings |
| `pyproject.toml.template` → `pyproject.toml` | Project name, dependencies, module map, coverage omit list |
| `docs/PRD.md` | Your PRD — this is what `prd-to-issues` reads |

For non-Python projects, `ci.yml` can be omitted or stubbed. Decide before dispatch whether you want a CI gate or pure auto-merge on any push.

> **Key `agent-dispatch.yml` notes:**
> - Requires `mode: agent` on the Claude Code action — without it, `workflow_dispatch` events fail
> - Sequential dependency gate: checks that the predecessor issue (N-1) is closed before running
> - Uses `GH_PAT` (not `GITHUB_TOKEN`) for PR creation — the built-in token can't trigger downstream workflows

---

### Step 5 — Add Your PRD

Copy your PRD into the repo as `docs/PRD.md`. This is the input the `prd-to-issues` workflow reads — without it, nothing gets generated.

```bash
cp /path/to/your-prd.md docs/PRD.md
```

> The `prd-to-issues` workflow triggers automatically when `docs/PRD.md` is pushed to `main`.
> Don't push yet — finish Steps 6–7 first so secrets and labels are in place before the workflow fires.

---

### Step 6 — Create the Labels

```bash
gh label create "agent-task"   --color "0075ca" --description "Ready for agent dispatch"                       --repo <your-org>/<repo-name>
gh label create "harness-gap"  --color "e4e669" --description "Missing capability — blocks agent, needs human" --repo <your-org>/<repo-name>
gh label create "human-review" --color "d93f0b" --description "Requires human judgment before merge"           --repo <your-org>/<repo-name>
gh label create "gc"           --color "0e8a16" --description "Garbage collection / entropy pass"              --repo <your-org>/<repo-name>
```

> The `agent-task` label is the dispatch trigger. Do not apply it to an issue until its predecessor is closed — the gate will halt the run, but it's cleaner not to trigger it at all.

---

### Step 7 — Commit and Push

```bash
git add .
git commit -m "feat: harness scaffold — AGENTS.md, workflows, labels"
git push -u origin main
```

---

### Step 8 — Verify

```bash
gh workflow list --repo <your-org>/<repo-name>
```

Expected output:
```
Agent Dispatch    push  .github/workflows/agent-dispatch.yml
CI                push  .github/workflows/ci.yml
```

> If workflows don't appear, the YAML has a syntax error GitHub is silently rejecting. Wait a minute and run again — GitHub can lag on registration.

---

### Step 9 — Generate Issues from Your PRD

The `prd-to-issues` workflow fires automatically when `docs/PRD.md` is pushed (which happened in Step 7). If you need to re-trigger it manually, use the Actions tab. Review the generated issues before dispatching — verify sequencing and the dependency chain.

---

### Step 10 — Dispatch Issue #001

Apply the `agent-task` label to Issue #001. Agent Dispatch fires automatically.

```bash
# Watch the run live
gh run watch --repo <your-org>/<repo-name>
```

Expected PR branch: `claude/issue-<N>-<slug>`

### Common Failure Modes

| Symptom | Cause | Fix |
|---|---|---|
| `Tag mode cannot handle workflow_dispatch events` | Missing `mode: agent` on Claude Code action | Add `mode: agent` to `agent-dispatch.yml` |
| `Halt — predecessor not closed` | Gate fired but prior issue still open | Close predecessor, re-apply `agent-task` label |
| `Permission denied` on PR creation | `GITHUB_TOKEN` used instead of `GH_PAT` | Confirm `env: GH_TOKEN: ${{ secrets.GH_PAT }}` is set |
| Workflows not in Actions tab | YAML syntax error | Validate with `gh workflow list`; check Actions tab for parse errors |
| Agent runs but makes no commits | Claude Code not installed on repo | Re-install at github.com/apps/claude |
| Coverage gate failing on stub modules | `pyproject.toml` omit list missing stub paths | Add stub module paths to `[tool.coverage.run] omit` |

---

### Backfilling Learnings from Existing Projects

If you've already built a project with the harness (or a similar agent-driven workflow), extract learnings retroactively:

```bash
python scripts/backfill_learnings.py /path/to/completed-project --output docs/learnings
```

This analyzes git history, compares issue specs against delivered PRs, identifies iteration patterns, and generates structured learning documents that feed the next `prd-to-issues` cycle.

## Case Study: playlist-migrate

The harness was validated end-to-end on [playlist-migrate](https://github.com/jtmurphysr/playlist-migrate), a CLI tool that migrates Spotify playlists to Apple Music. The issue specs and compound learnings from this project are preserved in `docs/examples/playlist-migrate/` as reference implementations.

- **27 sequential issues** dispatched, implemented, and auto-merged
- **0 human-authored lines of code** — all agent-generated
- **3,685 lines of tests** across 9 test files
- **92% track match rate** on real production data
- **4 clean passes, 3 iterations** — iteration rate improved as learnings accumulated

## Claude Code Hooks

`.claude/hooks/` holds two lifecycle hooks that run for anyone working on this repo with Claude Code. They are deterministic: they fire whether or not the model cooperates.

| Hook | Event | Behaviour on its own failure |
|---|---|---|
| `inject-context.sh` | `SessionStart` | **Fails open.** Injects five sections of `AGENTS.md` (6,671 chars — the file exceeds the 10,000-char hook-output cap, so it is excerpted by heading name). A session without the preamble is degraded, not unsafe, and `SessionStart` cannot block anyway. |
| `gate-done.sh` | `Stop` | **Fails closed.** Runs `validate_harness.py` then `pytest`, cheapest first, mirroring CI. The model declaring completion is a claim; a green suite is a receipt. |

Both source `lib/preamble.sh`, whose contract is that **helpers return non-zero and never exit** — exiting from inside `$( )` kills only the subshell, after which the hook proceeds to `exit 0` and allows the call it just printed `BLOCKED` for.

Two things worth knowing before editing them:

- **`exit 2` blocks; `exit 1` does not.** `validate_harness.py` exits 1 on violations, which is correct for CI and inert in a hook — `gate-done.sh` translates it. Wire that script in directly and the gate silently passes every violation it finds.
- **`CLAUDE_PROJECT_DIR` must be checked before the `source`.** `die_closed` lives in the file that line loads, and both `set -u` and `${VAR:?}` exit 1 there — non-blocking. A fail-closed hook with that bug silently is not there.

```bash
.claude/hooks/test-hooks.sh    # 27 assertions, one per bug that actually shipped
```

That suite runs in CI as **Hook Guards** and is a required status check, so a broken guard blocks the merge rather than reporting into the void.

The reasoning behind all of this is written up in [claude-code-hooks-guide](https://github.com/jtmurphysr/claude-code-hooks-guide), which uses these two hooks as its worked examples.

## Human Role

You are not writing code. You are:

- **Specifying intent** — PRDs, domain warnings, architectural constraints
- **Provisioning credentials** — API keys, secrets, environment configuration
- **Validating outcomes** — does the built thing do what you meant?
- **Evolving the constitution** — updating AGENTS.md when the harness learns something new

Everything else is delegated.
