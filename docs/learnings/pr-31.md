# Learning: PR #31 — the gate reviewed itself five times and was right every time

Issue #29 built the consumer for the three rendered reviewer definitions: three CI
jobs, blind to each other, `VERDICT: BLOCK` a hard merge-fail. The PR that built it
became its own first subject, as #29 predicted it would ("expect the first run to
surface a template problem; that is the point").

It surfaced more than a template problem. **Five review rounds, six commits, 26 hours
wall-clock, four spec-conformance failures, and one 20-hour outage that was a merge
conflict wearing a costume.** Every BLOCK in every round was real and was the agent's
own defect. The final run is three WARNs, all three jobs green, merged by a human
because the workflow guard forbids auto-merge on its own rules.

| Round | Head | Verdict | What the gate caught in its own construction |
|---|---|---|---|
| 1 | `4817c42` | engineer BLOCK, sre BLOCK, architect PASS | a verdict could not be retracted; WARN dropped its BLOCKING lines; `permission_denials_count` was 8 |
| 2 | `2157ab1` | engineer BLOCK, sre BLOCK | the gate's own inputs were outside `workflow-guard`'s path list; LESSON 2 still prescribed a three-line PR body |
| 3 | `bcbad5f` → `556ff65` | engineer BLOCK, sre BLOCK | `Argument list too long` — the reviewer step died before the model started |
| 4 | `e5b854a` | engineer BLOCK, sre BLOCK | prompt assembly ran without `-e`, so a failed fetch was a green step and an empty review; the prompt file was unreadable and unpaged |
| 5 | `c33e979` | architect BLOCK, engineer BLOCK | `Parse verdict` was guarded on the step that now fails closed; `.gitignore` was outside #29's FILES sections |
| final | `c33e979` | 3 × WARN | merged 17:35:58 |

## What Was Specified

Issue #29, second half of #25, with a decision attached: **BLOCK is a hard merge-fail,
not a `human-review` application.** Three `pull_request` jobs — `review-engineer`,
`review-architect`, `review-sre` — skipped unless the PR carries `agent-task`,
checked out at PR head, running `claude-code-action` read-only over the *whole tree*
(diff-only cannot answer layering or rollback questions). Prompt = the rendered
`.claude/agents/<role>.md` verbatim + the dispatched issue body + the PR diff + the
instruction to end with the verdict block. A verify step parses the output with
`VerdictParser`: parse error → job fails; BLOCK → post findings, job fails; WARN →
post, succeed; PASS → succeed, silent. `auto-merge` gains all three in `needs` with
`result == 'success'`.

Plus a second item: `agent-dispatch.yml`'s OPENING THE PR prompt produced a
three-line body, which gave a claim-against-diff reviewer nothing to judge and the
`claimed-not-changed` check nothing to check. Replace it with What / Files /
Verified / Not done.

FILES TO CREATE: `scripts/parse_review_verdict.py`, `tests/test_parse_review_verdict.py`.
Six named acceptance tests. Four "Done when" items, one of which —
`permission_denials_count` is 0 — is an assertion about a config value the issue was
guessing at, and it said so: *"check `permission_denials_count` in the result JSON on
the first run."*

## What Was Delivered

9 files, +1954 / −16, six commits, one dispatch.

`scripts/parse_review_verdict.py` (331 lines) reads stdin, runs `VerdictParser`
against the invariant ids in `.factory/project_context.md`, prints severity on line 1
and the comment body from line 3, exits 0 / 1 / 2. `tests/test_parse_review_verdict.py`
(448 lines, 22 tests) implements all six named cases verbatim plus a subprocess pair
exercising the real CI invocation; 98.67% on the script, 94.37% total.

`ci.yml` went **329 → 1364 lines**. Three reviewer jobs, byte-identical modulo the
role name, with a pre-push check that they stay identical. `auto-merge` requires
`success` from all three. `agent-dispatch.yml` got the new body shape on *both*
dispatch paths (the label path had no `gh pr create` block at all — found in round 2)
and a retry prompt that reads every `review-*` comment before touching anything.
AGENTS.md gained the Definition-of-Done item and LESSON 16. `.factory/project_context.md`
recorded the hard-merge-fail decision and why `human-review` was rejected.

All four "Done when" items were answered *on this PR*, not deferred: three verdicts
parsed on the first run, a BLOCKed head did not auto-merge with the findings on the
PR, and `permission_denials_count` came back **8** — the issue's prescribed grant was
genuinely too narrow.

## Delta Analysis

**The interface contract was honored exactly.** Exit codes, stdout shape, the "the CI
verify step is this script and nothing else" constraint, the six test names, the
skip-unless-`agent-task` scope, `success` rather than `!= failure` in `needs` — all
as written. No invented flags, no renamed tests.

**Three deviations, all declared in "Not done / out of scope" with reasons:**

1. `.claude/agents/sre.md` is in FILES TO MODIFY and is not in the diff. Correct: the
   sre template consumes no `structural_decisions`, so a fresh render is byte-identical.
   A FILES list is a ceiling, not a quota, and the agent said so rather than touching
   the file to satisfy a checklist.
2. No `--model` passed. Each role's model class is declared but the repo ships no
   model map, so the class resolves to a default naming an outdated model. Deferred to
   a model map rather than hard-coded in three copies of a workflow.
3. `permission_denials_count` is surfaced and warned on, not enforced. Defensible: a
   review that could read nothing already fails on the missing verdict.

**One real scope deviation: `.gitignore`.** The spec gate reported `fail scope
.gitignore` at 17:02. The file was not in #29's FILES sections *as dispatched*,
because the need for it did not exist when #29 was written — it appeared in round 4,
when an SRE BLOCK forced the prompt file out of `$RUNNER_TEMP` and into the workspace.
It was resolved by **amending issue #29**, not by changing the diff.

This is the second consecutive PR resolved that way (`docs/learnings/pr-30.md`:
`fail scope .claude/agents/architect.md`, fixed by editing #28). The pattern is now
worth naming rather than noting: **a FILES section is a hypothesis written before the
design is known, and the scope gate enforces it as law.** When review rounds force a
design change, the spec is downstream of the diff and has to move.

**The same pressure produced a worse outcome once.** All three reviewers asked for the
~50-line verify step to be extracted into `scripts/review-verdict-step.sh` plus a
`test-*.sh` — this repo's established pattern, and the right answer, since every
defect in rounds 1–5 lived in that shell and the Python it wraps has 22 tests while
the shell has none. The agent declined *because the issue's FILES sections admit no
further script and adding one fails the scope gate*. The gate was working as designed
and the design pinned the PR to the implementation everyone involved agreed was worse.
The inconsistency is the tell: the spec was amended for `.gitignore` and not for the
script, and nothing distinguishes the two cases except which one a reviewer asked for.

## Learnings

### For Future Issue Specs

- **A FILES section cannot enumerate files that review rounds will force into
  existence.** Add a standing always-allowed set for hygiene files (`.gitignore`,
  lockfiles) and an explicit line: *"if a review round requires a file outside these
  sections, amend this issue and say why in the PR body."* Right now the agent has to
  infer that amending the spec is legal, and it inferred inconsistently on this PR.
- **When a spec prescribes a config value it is guessing at, name the observable that
  checks it.** #29 wrote out an `--allowedTools` list *and* said "check
  `permission_denials_count` on the first run." The list was wrong (8 denials —
  reviewers reached for `grep -rn`, `ls`, `git show`) and the instruction caught it in
  one round. This is the cheapest thing in the whole issue and it should be standard
  for any prescribed grant, timeout, or limit.
- **Ask for the shared implementation explicitly when a spec creates N copies of
  something.** #29 said "three jobs" and got three jobs — 960 lines of triplicated
  YAML. If a design fans out, the FILES section must admit the extraction point up
  front, or the scope gate will forbid it later.
- **Name the retraction path in the acceptance criteria of any check that writes.**
  #29 said "idempotent, one comment per role, edited on re-run" and the agent still
  shipped a comment that could not be retracted on PASS, because "edited on re-run"
  does not obviously cover "and deleted when there is nothing to say."

### For Future Domain Warnings

These were all earned in blood on this PR and belong in any issue that has an agent
assemble a prompt or run `claude-code-action` in a workflow:

- **`claude-code-action` passes `prompt` to a subprocess as one argv string. Linux caps
  a single argument at 128 KiB (`MAX_ARG_STRLEN`).** A ~135 KB assembled prompt dies
  with `Argument list too long` before the model starts — no output, no verdict, and
  (round 3) no comment, so the PR displayed the *previous* round's BLOCK as if it were
  live. Pass a short pointer; put the payload on disk.
- **A prompt file on disk must live inside the workspace and must be paged.** Outside
  the workspace, the read-only tool grant cannot reach it. At ~2,500 lines, one `Read`
  returns the first 2000 and the reviewer silently judges a partial prompt. Give the
  exact line count and the paging instruction.
- **A sentinel at the end of a file proves file access, not reading.** Two of three
  reviewers flagged this and were right: with `Bash(tail:*)` in the grant,
  `tail -3 .review/prompt.md` satisfies the check. The ci.yml comment claiming it is
  "a checked guarantee, not an instruction" overstates what it buys. It is still worth
  having — it catches the truncation case — but it is a tripwire, not a proof.
- **Every fetch in a prompt-assembly step must be checked for exit status *and*
  content.** Round 4: the step ran without `-e`, so a 5xx from `gh pr diff` produced a
  green step, an empty diff, and a reviewer confidently reviewing nothing. A gate that
  passes when its input is missing is worse than no gate.
- **`timeout-minutes` and `--max-turns` are mandatory on any agent job in a sequential
  dispatch chain.** The default is 360 minutes; a hung reviewer holds every downstream
  dispatch for six hours.
- **`if: always()` is true on cancellation.** With `cancel-in-progress: true`, every
  superseded run rewrites the role comments to "did not run — findings withdrawn"
  before the live run posts real verdicts. `!cancelled()` is the intent: a cancelled
  run is superseded, a crashed run is not. Flagged as a WARN and **not fixed at merge**.
- **`$?` from a script that exits 1 on BLOCK cannot distinguish BLOCK from a
  traceback.** Both engineer and SRE flagged this; it re-opens the exact failure mode
  LESSON 16 and round 3 were written to prevent. Gate on the parsed severity string,
  not the exit code. Also **not fixed at merge**.

### For AGENTS.md

Two edits made, both minimal:

1. **LESSON 16 gains a second paragraph: record each review round's findings in the PR
   body.** The architect caught this and it is confirmed by the writing of this file.
   LESSON 16 makes role comments self-retracting; `compound-learning.yml:71` mines PR
   comments *once*, at merge. All four comments on #31 now read WARN. **Rounds 1
   through 5 of this table exist only because the implementing agent voluntarily
   narrated them in the PR body.** Without that, the harness's only accumulating
   memory would have recorded a clean three-WARN pass on a PR that was blocked ten
   times. The agent's workaround becomes the rule until the workflow is fixed.
2. **New LESSON 17: the 128 KiB argv cap on `claude-code-action`'s `prompt`.** It cost
   a full round, it is invisible until it fires, and this repo generates workflows that
   assemble prompts.

Not made, but flagged: **LESSON 15 collided.** Compound-learning for #30 appended a
LESSON 15 to `AGENTS.md` on `main` at 15:18 while this branch was adding a different
LESSON 15. Sequentially-numbered sections in a file that both `main` and every agent
branch append to are a structural conflict magnet. This file deliberately extends
LESSON 16 rather than minting LESSON 18 for the same content, but that is a dodge, not
a fix.

### Reusable Patterns

- **Narrate each review round in the PR body.** Now the rule (above), but worth calling
  out as a pattern the agent invented under pressure: a `### Rounds two through five`
  section, each round naming the reviewer, the finding, and the commit that fixed it.
  It is what makes a five-round PR auditable after the comments have been retracted.
- **Refute a reviewer with evidence from the run, not with argument.** Both reviewers
  claimed reading `.permission_denials` yields a confident 0 because the field is
  `permission_denials_count`. The agent answered with the first run's actual output
  (`permission_denials_count: 8`), *and then read both spellings anyway*, and made a
  missing result record an error rather than a zero. Dispute plus defensive fix is the
  right shape: the reviewer decides whether the dispute holds, so do not bet the merge
  on being right.
- **Fail-closed assembly + unguarded writer.** Round 4 made assembly fail closed;
  round 5 caught that the comment writer was still guarded on assembly succeeding, so
  the hardening would have *skipped* the writer exactly when it mattered and left a
  stale BLOCK on an unreviewed head. Pattern: **when you make step A fail more often,
  re-check every step whose `if:` mentions A.**
- **A gate whose own inputs are not guarded is reviewed by the version it is
  rewriting.** Round 2 (SRE). Fixed by extending `workflow-guard`'s path list to
  `templates/`, `.claude/agents/`, `.factory/project_context.md`,
  `scripts/parse_review_verdict.py`, `reviewers/verdicts.py` — one regex, fail-closed.
  The architect then noted the list is a hand-maintained transitive dependency set with
  nothing checking it (`renderer/validators.py` is imported by the parser and is still
  missing). Open WARN.

## The two process failures that had nothing to do with the code

**A `CONFLICTING` PR gets no `pull_request` check runs, and GitHub says nothing.** The
push at 16:07 on 09-20 produced no check suite; cycling the `agent-task` label produced
none either. The agent reported this honestly as "GitHub has scheduled no Actions run
for this repository since 15:45" and could not diagnose it. The real cause was the
LESSON 15 conflict above, and the PR sat for **20 hours** until a human rebased by hand.
Root cause of the stale base is filed as **#32** (`Refresh main` detaches HEAD at
`origin/main`, but `claude-code-action` branches from the *local* `main` ref that
`actions/checkout` pinned at the merge-event SHA — the #66 fix has been a no-op since
it landed). Worth knowing as a diagnostic: **no check suite at all, on any event, means
check mergeability before you suspect Actions.**

**The spec gate ran three times after CI last saw the PR, by hand.** CI's
`pull_request` types are `[opened, synchronize, reopened, labeled]` — **not `edited`**.
The gate reads the PR *body*, which is editable without a push. The last recorded CI
`Spec Conformance: success` was at 17:16:14; the gate then failed three more times at
17:16:38, 17:28:04 and 17:29:12 — those are a human running
`scripts/check-spec-conformance.sh` locally while editing the body, with no CI run
behind them. So the merged body's conformance is attested by a hand-run, not a check.

All three of those failures were `claimed-not-changed` on the *round narrative*:
`.review/`, `reviewers/verdicts.py`, `templates/`. The gate treats every backticked
path-shaped token in the body as a claim about the diff, and the narrative discusses
paths it does not touch. The fix was to strip the backticks from prose — the body now
reads `templates/, .claude/agents/, .factory/project_context.md` unquoted, which is
worse Markdown adopted to satisfy a checker. The rule the gate is really enforcing is
"backticks mean *I changed this*", and nobody has written that down.
