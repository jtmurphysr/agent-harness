# Learning: PR #30 — the gate refused its own PR, twice, and both refusals were right

PR #30 built `scripts/check-spec-conformance.sh` and then immediately became its first
subject. The gate reported `unresolved no-files-section #28` at 14:59 and
`fail scope .claude/agents/architect.md` at 15:04 — **on the PR that introduced it** —
before reading `pass` at 15:05:57 and being merged by a human at 15:13.

The thing worth recording is *where* the iteration happened. Zero commits were pushed
after the first two (`151b51b`, `b8a3d4e`, 14 seconds apart). Every other check —
Lint & Types, Tests, Harness Structure, Hook Guards, Workflow Change Guard — went green
on that first push and never ran again. **Both red verdicts were fixed by editing issue
#28, not by editing the diff.** This is a required-iteration cycle in which the agent's
output was never the thing that changed.

## What Was Specified

Issue #28, "Verdict contract in the reviewer templates, and a deterministic
spec-conformance gate" — the first half of #25, in two parts.

**Part A.** `templates/*.template.md` asked reviewers for no output format, and
`reviewers/verdicts.py` inferred BLOCK by keyword-sniffing the `## Bad` section for
`block`, `critical`, `security`, `breaking`, `data loss`, `corrupts`, `irreversible`.
"Nothing critical here" parsed as BLOCK; "this deletes the ledger on restart" parsed as
WARN. Ship a mandatory literal `## Verdict` / `VERDICT:` / `BLOCKING:` / `WARNINGS:`
block, have the parser read it literally, delete `_determine_severity` and both keyword
tables. BLOCK legal only with a citation to a declared invariant id, a spec section, or
a named section of the dispatched issue. Missing `VERDICT:` line → parse error → never
a PASS.

**Part B.** `scripts/check-spec-conformance.sh <repo> <pr>` answering five questions
with no model call: closing keyword present; closing keyword names the dispatched issue;
changed files ⊆ the issue's FILES sections plus an always-allowed set; every
`test_<name>` in ACCEPTANCE CRITERIA present in diff or tree; every backticked path in
the PR body present in the diff. One line of stdout, `pass` | `fail <reason>` |
`unresolved <reason>`. New `spec-conformance` CI job, required by `auto-merge`, fail
closed.

**As dispatched at 14:34, issue #28 had no `FILES TO CREATE` and no `FILES TO MODIFY`
section.** It was prose. The sections now visible in the issue body were added after
the PR opened — the body says so itself, in a parenthetical inside the FILES TO CREATE
list it is describing.

## What Was Delivered

15 files, +1681 / −429, two commits, one dispatch, nothing from the issue left out.

**Part A.** `templates/_shared/verdict_block.partial.md` (new) carries the literal block
and its rules, included as the **last** thing in all three reviewer templates —
`tests/test_templates.py` asserts the include is last, because position is part of the
instruction. `templates/_shared/output_contract.partial.md` gains "severity is declared,
not inferred." `reviewers/verdicts.py` takes severity from the `VERDICT:` line and
nowhere else; `_determine_severity` and both `block_indicators` tables are gone; module
at 100% coverage. Seven parse-error cases, each with a test: no `VERDICT:` line; the
literal `PASS | WARN | BLOCK` echoed back; BLOCK with no citable BLOCKING line; BLOCK
with an empty BLOCKING list; WARN with no warnings; PASS with findings; a citation to an
invariant id the project never declared. Two regression tests pin the old failure in
both directions. `.claude/agents/{architect,engineer,sre}.md` re-rendered via
`scripts/render_own_agents.py`, not by hand.

**Part B.** `scripts/check-spec-conformance.sh` (335 lines) plus
`scripts/test-check-spec-conformance.sh` (392 lines, 28 tests on real shapes — PR #103
against the #56 issue body, a GC-filed body with no FILES section, a `FILES TO MODIFY`
split into a read-for-context half and a modify half). The scope check reads the
**modify half only**; a path listed under "read for context" is not permission to change
it, and there is a test for exactly that. CI job added, `auto-merge` requires
`needs.spec-conformance.result == 'success'` — skipped is not success.

`renderer/compose.py` and `reviewers/dispatch.py` untouched, as the issue required.

## Delta Analysis

**The diff matched the spec. The spec did not match itself.**

| Event | Time | Cause |
|---|---|---|
| Dispatch | 14:34 | issue #28 is prose, no FILES sections |
| PR opened, both commits pushed | 14:55 | — |
| `unresolved no-files-section #28` | 14:59 | the gate, reading its own dispatching issue |
| `fail scope .claude/agents/architect.md` | 15:04 | FILES sections added, but without the three rendered agent files |
| `pass` | 15:05 | FILES sections amended again to list them |
| Merged by a human | 15:13 | Workflow Change Guard applied `human-review` — by design |

Three findings fall out of that table.

**1. The agent predicted both failures in its PR body, before they happened, and
declined to patch around them.** The body's closing section reads: *"The new gate will
report `unresolved no-files-section` **on this PR**, because issue #28 is written as
prose and declares no FILES sections. That is the gate working as specified — fail
closed on an issue that is not a spec — not a defect in the script."* It then names the
open design question (should prose harness issues carry FILES sections, or should the
job treat `unresolved` differently from `fail`?) and says *"I implemented the issue's
stated behaviour rather than choosing for you."* A special case for "the PR that
introduces the gate" would have been the easy, wrong fix and would have shipped a hole
in the gate on day one. This is the model of what a PR body is for; see § Reusable
Patterns.

**2. The gate reads the issue body live, and the issue body is mutable.** Both red
verdicts were cleared by editing issue #28 — the second time by appending the exact
three paths the diff had already touched. The gate's `pass` on PR #30 therefore
certifies conformance to a spec that was reverse-engineered from the delivery. Nothing
in the harness records what the issue said **at dispatch time**, so nothing can tell
"the agent stayed in scope" apart from "the scope was moved to fit the agent." On this
PR the edits were honest bookkeeping by the repo owner. The mechanism does not know
that, and the next one may not be.

**3. The `.claude/agents/` always-allowed rule is dead code in this repo, and it is what
caused the 15:04 failure.** `scripts/check-spec-conformance.sh:264` sets
`agents_docs_changed` by grepping the changed-file list for `^docs/agents/`, and
`.claude/agents/*` is allowed only when that is true. **There is no `docs/agents/` in
this repository.** `scripts/render_own_agents.py:51` renders `.claude/agents/` from
`templates/` and `.factory/project_context.md` (PR #23). So any PR that changes a
reviewer template must re-render three generated files, and the rule that exists to
permit exactly that can never fire. It fired `fail scope` on the first PR to exercise
it. The agent implemented this faithfully — the issue spelled out "`.claude/agents/`
when `docs/agents/` changed" verbatim. The defect is in the spec, and it is still live
on `main`.

The branch is also **untested**. The 28-test suite covers the always-allowed set for
`docs/learnings/`, `AGENTS.md`, and `pyproject.toml` in both directions
(`scripts/test-check-spec-conformance.sh:235,261,273`) and has no case for
`.claude/agents/` at all. An untested branch whose predicate is unsatisfiable is
indistinguishable from a deleted one.

## Learnings

### For Future Issue Specs

**Prose is no longer a legal issue form in this repo.** As of this merge, an issue
without `FILES TO CREATE` / `FILES TO MODIFY` returns `unresolved`, and `auto-merge`
fails closed on it. Every issue in the dispatch queue that was written before PR #30 is
now un-mergeable-by-robot until its body gains a FILES section. This is a retroactive
requirement applied by a merge, which is the sharpest kind: it did not break anything
today, it broke everything still queued. Sweep the queue before dispatching the next
one.

**Do not copy a path convention into a spec without checking it resolves.** The issue
wrote "`.claude/agents/` when `docs/agents/` changed" — a plausible sentence describing
a directory layout this repo does not have. It read as authoritative, the agent
implemented it exactly, and it cost a CI cycle on its own PR. When a spec names a path
as a *predicate* rather than as a file to edit, the spec author owes an `ls`. Matching
pattern in pr-7.md: `ALLOWED_IMPORTS` sat pointed at example modules for three cycles
and the linter walked zero files. Both are the same failure — **a rule whose subject
does not exist passes silently and protects nothing.**

**Name the verdict boundary when a gate has more than two outcomes.** The issue
specified `unresolved` as a distinct verdict and said the caller fails closed on it, but
never said whether `unresolved` should read differently from `fail` to a human. The
agent implemented the letter and escalated the question in the PR body. That was right,
and it would have been cheaper as a line in the issue.

### For Future Domain Warnings

**`gh pr view --json` and `gh issue view --json` go through GraphQL, which needs
`read:org`. `GH_PAT` does not have it.** This has now bitten three separate actors: the
Workflow Change Guard on its first run (recorded in `scripts/check-spec-conformance.sh:55`),
the author of that script (who documented it and used `gh api` throughout), and the
compound-learning agent writing this file, whose first command was `gh pr view 30
--comments` and got three scope errors. Every GitHub read in this repo must go through
`gh api` REST. Promoted to AGENTS.md as LESSON 15 — see below.

**A generated file in a diff is not scope creep.** `.claude/agents/*.md` are rendered
output. An agent that changes a reviewer template and does *not* re-render them has left
the tree inconsistent; PR #23 exists because those files had drifted 106 lines from
their templates. Any scope rule written for this repo has to treat template → rendered
agent as one unit, and any issue spec touching `templates/` should list the three
rendered files in FILES TO MODIFY until the always-allow rule is fixed.

**A gate that reads mutable input certifies nothing about the past.** Worth stating
wherever a future gate is specified: if the check reads a live GitHub object, say in the
issue what prevents the object from being edited to produce the answer. The honest
options are to snapshot the spec at dispatch (the dispatch comment already exists as a
natural place to pin it) or to accept the gate as advisory and say so.

### For AGENTS.md

**Added LESSON 15** — every GitHub read uses `gh api` REST, never `gh pr view --json` /
`gh issue view --json`, because those route through GraphQL and require `read:org` that
`GH_PAT` deliberately lacks. Three occurrences, one of them in this session; that is a
rule, not an anecdote.

**Not added, deliberately:** a lesson about the spec-conformance gate's semantics. The
gate is one merge old, its `.claude/agents/` rule is known-wrong, and writing its
current behaviour into the constitution would freeze a bug. AGENTS.md should gain a
Definition-of-Done line about FILES sections once the issue *template* enforces them —
fixing the template is the load-bearing change, and a constitution line is the
follow-up, not the substitute. Tracked in Suggested Actions.

### Reusable Patterns

**The gate-script contract, now at three instances — it is a repo pattern, not a
coincidence.** `resolve-predecessor.sh`, `refuse-held-issue.sh`, and now
`check-spec-conformance.sh` all share:

- exactly one line on stdout; the caller parses a word, not a log
- exit 0 for **every** verdict including failure; non-zero reserved for the script
  itself breaking, so "gate said no" stays distinguishable from "gate is broken"
- a third verdict (`unresolved`) for "cannot answer", which the caller fails closed on
- every external lookup behind a `GH_*_LOOKUP` env override naming a function, so the
  test suite runs hermetically with no network and no fixtures checked into CI
- a companion `scripts/test-<name>.sh` built from **real** issue and PR bodies

The fourth gate script should not be designed; it should be copied. Worth a short
section in AGENTS.md once someone writes the fourth one and confirms the shape holds.

**A deterministic check beats a reviewer for any question with a deterministic answer.**
The script's own header makes the argument better than a summary can: *"A model reading
a diff is the wrong tool for a question a script can answer, and it is worse than a
script, because it will sometimes say yes."* Three failures in the lessons list had been
charged to "no reviewer" and every one of them was mechanical. Before specifying a
reviewer-based check, ask whether the answer is computable; if it is, the reviewer is
strictly worse and costs a model call.

**Declared, not inferred.** The Part A fix generalizes past verdicts: when a machine
reads model output, the machine reads a declared field in a fixed position, and prose
anywhere else in the response cannot move it. The parser fails closed on a malformed
declaration rather than guessing, and a parse error is a failed review, never a PASS.
Any future structured extraction from a model response in this repo should take this
shape.

**Pin a deletion with a test, not a comment (LESSON 11, applied cleanly).**
`tests/test_verdicts.py` reads its own module with `inspect.getsource` and fails if
`_determine_severity` or `block_indicators` reappears. The keyword table was not merely
removed; its return was made a test failure. This is the right move whenever a fix
consists of deleting a mechanism that looked reasonable — the next agent will otherwise
reintroduce it in good faith.

**Position as instruction, asserted.** The verdict partial must be the *last* include in
each template, and `tests/test_templates.py` asserts it. Prompt structure that carries
meaning should be tested like any other contract, or the next template edit will bury
it mid-file and nothing will notice.
